  ## FINDINGS

  **B1 (blocker) — The published payment manifest tells agents to pay a literal template string.**
  `site/public/.well-known/x402.json:18` publishes `"recipient": "RUNTIME_ENV:COMPANY_WALLET"` — an unexpanded placeholder. `llms.txt:15` and `sdk/README.md:44` both instruct agents that "the 402 challenge body is always authoritative" and to check the manifest for the signer/recipient; an autonomous agent that cross-checks the challenge against the manifest (the only safe behavior) gets a garbage payTo and must abort, and one that doesn't cross-check is one DNS/TLS compromise away from paying an attacker. Compounding it: `x402.json:3` says `"environment": "staging"` while `llms.txt:11` says "ENVIRONMENT: production … real USDC" — the two machine-facing documents disagree about whether real money is involved. Better: generate `x402.json`, `llms.txt`, `openapi.yaml`, and the Pricing page from a single route-config source of truth at deploy time, with a CI assertion that the published recipient equals the `payTo` the routes actually stamp.

  **B2 (blocker) — The entire public discovery surface teaches a wire dialect the roadmap deletes with zero sunset, and no standard x402 client can pay production today.**
  `llms.txt:20-28`, `openapi.yaml:75-99`, `site/src/pages/Docs.tsx:4-21`, and `sdk/src/index.js:100-112` all document the bespoke body-authoritative `X-PAYMENT` JSON dialect (server-minted nonce, private error codes `REPLAYED_NONCE`/`INVALID_SIGNATURE`). The vendored spec is header-normative (`specs/x402/http.md:14`, client-owned 32-byte nonces, §9 taxonomy strings). The v2 route is KV-dark in production ("v2 dark 404", `reviews/kaizen-log-2026-08-19.md:12`), and the decision is already taken to **hard-cut** legacy with no sunset machinery (`reviews/cdp-findings.md:48-56`). So: today a conformant `@x402/fetch` agent pointed at the marketed URL cannot pay at all; after Stage 5, every agent that learned from llms.txt (including LLM training caches, which never expire) calls a dead route with no `Deprecation`/`Sunset` header because G1's RFC 8594 headers were tied to the sunset path that was skipped (`reviews/plan-rev3-2026-08-19.md:31`). Better: even at zero measured traffic, keep `/v1/*` as a thin shim that rewrites into the v2 pipeline and emits `Sunset` + a `PAYMENT-REQUIRED`-compatible 402, and ship the v2 discovery docs *before* the flip, not at Stage 5.

  **M1 (major) — The marketing site asserts a mainnet settlement that the project's own prod audit says never landed in the ledger.**
  `site/src/pages/Trust.tsx:96` claims "First mainnet settlement — 2026-08-17 · $0.005 · Base mainnet · block 50072738 · facilitator-free," but `reviews/cdp-findings.md:52` records prod `code402-ledger-prod`: **0 SETTLED, 1 PENDING_SETTLEMENT never confirmed**. Either the public proof is the unreconciled PENDING row (in which case the "append-only ledger" and I4 chain-truth story failed to record the company's flagship proof transaction — and the pre-cut obligation to reconcile it, `cdp-findings.md:60`, is still open while the tx is already marketed), or the claim is unverifiable. For an evidence-first brand whose badge spec promises "we cannot quietly rewrite history" (`specs/VERIFIED-BADGE.md:28`), this is the worst possible inconsistency. Better: no settlement is cited publicly until it exists as a terminal, evidence-carrying row (`resolution_tx`) in the prod ledger; add a CI/site-build check that every tx hash on Trust/Proof pages resolves against the ledger export.

  **M2 (major) — The Proof page advertises an XDR-1/JCS receipt scheme that the only published client cannot produce or verify.**
  `site/src/pages/Proof.tsx:110-117` claims "RFC 8785 (JCS) canonicalization … domain-separated commitment with a signed payment_ref … verifies offline." The shipped SDK implements a bespoke length-prefixed keccak commitment with no JCS anywhere (`sdk/src/index.js:47-62`) and recovers the signer over a **raw 32-byte hash with no EIP-191/EIP-712 domain separation** (`sdk/src/index.js:64-71`) — a signature format that is replayable across any protocol that interprets the same digest. An agent following llms.txt → SDK gets a client that cannot verify the receipt properties the site sells as the differentiator. Better: define the receipt as an EIP-712 typed structure (domain-separated, `payment_ref` bound), publish the typehash in `/.well-known/x402.json`, and make SDK verification of *that* the conformance test — the receipt scheme the site describes must be byte-reproducible from the SDK alone.

  **M3 (major) — The shipping SDK has no payee/asset policy gate; the crawler client fixed this exact hole and the fix never propagated.**
  Stage-3 red-team Break 2 (`reviews/stage3-c1-verdict-deepseek.md:51-67`) proved a malicious 402 can direct spend to an arbitrary `payTo`, and the C1 crawler client gained an `allowed_payees` gate. The public SDK still signs whatever the challenge says: `to: ch.recipient`, `verifyingContract: ch.price.token_address` (`sdk/src/index.js:157-169`), with only a chain-id check and an optional price cap — "challenge is authoritative" is marketed as a safety rail (`sdk/README.md:44`) when it is precisely the attack surface. A compromised origin, a hostile lookalike staging URL, or a misconfigured manifest drains the payer to any address. I2 ("no spend without policy", `plans/x402-design-logic.md:27`) is absent from the only client a stranger will actually run. Better: the SDK already fetches `/.well-known/x402.json` for the receipt signer (`sdk/src/index.js:88-98`) — pin `payTo` and `asset` from the same manifest, refuse any challenge that deviates, and ship a deny-by-default policy hook mirroring the crawler engine's predicate list.

  **M4 (major) — The fee model contradicts itself across files, and the pricing is underwater at list price.**
  `plans/x402-design-logic.md:84` parks batching "only if per-settle fees return (CDP is currently free; the problem doesn't exist)" — but `reviews/cdp-findings.md:22` already measured the fee: **$0.001 per onchain settlement past 1,000/month free**. Against list prices of $0.002–0.005/call (`llms.txt:95-96`), that is a 20–50% take rate, and `reviews/stress-2.md:8` burned the entire monthly free tier in a single 310-second test. Meanwhile CDP's `batch-settlement` scheme (thousands of offchain verifies, one onchain tx) is documented in the same findings file (`cdp-findings.md:27`) and parked anyway. Better: set a price floor ≥10× the marginal settle fee, and adopt `batch-settlement` (or the parked `upto`/session flow, `reviews/launch-checklist.md:56-58`) for sub-cent tools — the trigger the design-logic is waiting for already fired.

  **M5 (major) — A Durable Object per payment is the most expensive and most bug-prone part of the design, and D1 already does its job.**
  G3 keys a DO by `hash(from‖nonce)` (`reviews/plan-rev3-2026-08-19.md:41-44`): one DO instance minted per payment attempt, forever, with per-request billing — then the reconciler required a D1 claim-time bridge row anyway because the DO state wasn't queryable (`reviews/reconciler-spec-v1.md:98`), producing exactly the DO/D1-divergence bug class that dominated the reconciler gate (M1/M2, `reviews/reconciler-gate.md:15-17`). D1 is single-writer SQLite: `INSERT … UNIQUE(payer,nonce)` is the claim, and the guarded `UPDATE … WHERE status IN ('claimed','settling')` the reconciler already enforces (`reconciler-spec-v1.md:46`) is the transition law — mutual exclusion and absorbing terminals with one authority, no second system to diverge. Better: delete the claim DO; keep D1 as the sole claim authority with the UNIQUE constraint doing serialization, and the DO pattern reserved (if ever) for genuinely long-lived coordination.

  **M6 (major) — Hourly-only reconciliation strands paid-but-unserved clients for up to ~85 minutes when the fix costs one RPC call.**
  A phantom-settle payer gets `503 settlement_pending` and must wait for the lease (300s) plus the hourly cron (`reviews/reconciler-spec-v1.md:17,50`; lived end-to-end in `reviews/reconciler-e2e-report.md:15-18`). The disambiguator is a single `eth_getLogs` keyed by indexed `(authorizer, nonce)` (`reconciler-spec-v1.md:56`) — it can run inline the moment the already-used/ambiguous outcome is detected, resolving the entitlement in the retry the client is already making. The spec even parks event-driven reconciliation explicitly (`reconciler-spec-v1.md:97`). Better: on-demand targeted resolution on the ambiguous path (one log query, fail-soft to the cron), keep the hourly sweep as backstop, and add a chain-event webhook (Alchemy/QuickNode/Coinbase notifications) when volume justifies it — reconciliation becomes push-assisted, not calendar-bound.

  **M7 (major) — The TLA+ artifact proves a property the production system deliberately violates, and was stale within a day.**
  `specs/model/claim.tla:10` models five states; migration 0003 added three more terminal states the same day (`reviews/reconciler-spec-v1.md:33-46`). The model marks `receipt_pending` "absorbing" (`claim.tla:32`) though the reconciler's entire purpose is transitioning out of it, and the gate ratified a real absorbing-law violation (SettledReconciled→Settled, `reviews/reconciler-gate.md:30`) — so INV-B is false in production. Worse, the "invariants" are comments; only `Absorbing` is formalized (`claim.tla:37-40`), with no TLC config, no fairness, no multi-instance modeling, so INV-A ("settled at most once") is never actually checked. `LeaseExpires` resetting `settling → claimed` (`claim.tla:16-19`) permits a second `BeginSettle`, and the model cannot express the chain-level exactly-once that saves it. Better: regenerate the model from the D1 state machine (post-M5 there is exactly one), formalize INV-A as a real temporal property, and gate CI on the model's states matching the migration's enum — a model that drifts is worse than none.

  **M8 (major) — `mcp.json` is not an MCP manifest and no MCP server exists; a GTM phase is aimed at registries that will reject it.**
  `site/public/.well-known/mcp.json` is a bespoke tool catalog; the MCP registry expects a server implementing the MCP protocol (JSON-RPC `tools/list` etc.), and `plans/monetization-playbook.md:20` schedules "MCP registry submissions" for Stage-5 week. There is no MCP endpoint anywhere in the plans. Better: either stand up a real MCP server (a Workers MCP adapter over the existing tool routes is a day of work and makes "monetizable MCP tools" literally true), or delete the file and the Phase-2 line item.

  **m1 (minor) — Alarms render on a public web page and page nobody.** `reviews/reconciler-spec-v1.md:71-81` defines warn/page thresholds but the delivery mechanism is "surfaced on the live stats endpoint" (`/v1/ops/stats`, consumed by `site/src/pages/Proof.tsx:20`). A dead-man switch that requires a human to visit a marketing page is not a pager, and the endpoint simultaneously leaks breaker state and cancel counts to attackers probing the DoS surface. Better: cron-emit to a webhook/email on threshold breach; make the public endpoint a redacted subset.

  **m2 (minor) — Single trusted RPC can mint or hide entitlements; the parked quorum trigger misprices the risk.** `reviews/reconciler-spec-v1.md:97` parks multi-RPC until "settled value/day exceeds what a lying RPC could steal" — but a lying RPC can also *deny* legitimate entitlements (a refund/reputation cost, not theft) and fabricate `settled_reconciled` rows that serve paid content free. A two-provider compare on the log query is ~20 lines and kills the whole class; do it now rather than at a value trigger.

  **m3 (minor) — Cancel-probing is an alarm-fatigue DoS on the operator.** `reconciler-spec-v1.md:58,77` pages a human at ≥1 `failed_canceled` per run; an attacker can generate cancels against their own authorizations for Base gas pennies and force an investigation every hour. Better: aggregate by payer/cluster and page on rate or novelty, not on existence.

  **m4 (minor) — The replay path withholds the output the client paid for.** `sdk/src/index.js:120-122` returns `{replayed:true, receiptRef}` with no output; `llms.txt:28` documents the same. G2b already persists the full response for exactly this case (`reviews/plan-rev3-2026-08-19.md:34-36`). Better: idempotent replay returns the stored output + receipt + settlement tx (the design review already noted the tx gap, `reviews/design-review-consolidated-2026-08-19.md:22`).

  **m5 (minor) — SDK returns fabricated state:** `settlement: "PENDING_SETTLEMENT"` is a hardcoded literal (`sdk/src/index.js:216`), indistinguishable from a real status. Return the actual PAYMENT-RESPONSE/status_url or omit the field.

  **m6 (minor) — The `/verify` question is answered two opposite ways in binding documents.** Plan G9's deviation note records "we additionally call facilitator `/verify` before `/settle`" (`reviews/plan-rev3-2026-08-19.md:80-82`); `reviews/launch-checklist.md:47-50` (Option A, operator-accepted) skips `/verify` for LocalPass payments. Note also spec §7.1 says servers invoke `/verify` *only* when the declared flow's ordering includes it, and `upfront` omits it (`specs/x402/x402-specification-v2.md:304`) — so the G9 note describes a spec divergence that Option A then removed without updating the note. Pick one, update both documents.

  **m7 (minor) — Price/tool catalog disagrees with itself across four files.** Context-distill is $0.010 in `llms.txt:96` and `mcp.json:81` but $0.005 on `site/src/pages/Home.tsx:132`; `x402.json:21` says default 5000 while the standard tier is 2000; Home's "x402 Endpoint Prober" tool exists in no manifest. This is exactly the catalog-vs-live drift the company's own badge flags competitors for (`specs/VERIFIED-BADGE.md:39`). Fix via the single-source generation in B1.

  **m8 (minor) — The observatory dataset economics don't survive arithmetic.** `plans/paying-crawler-plan.md:35` caps mainnet probes at $10 total while claiming the delivery-reliability dataset "starts accruing here"; one sweep of 1,000 endpoints at $0.01 consumes the entire cap. Either the dataset is one sweep deep (no time series, no drift detection — the two things VERIFIED-BADGE sells) or the cap is fictional. Budget a per-week probe line item and say so.

  **m9 (minor) — Governance documents cited as binding authorities are absent from the repo.** `reviews/reconciler-spec-v1.md:83` gates merges "per PANEL.md"; `specs/VERIFIED-BADGE.md:66` derives hard rules from `OPERATING-CONTRACT.md`; neither file exists in the tree (nor do the `crates/` sources every verdict cites). A gate process whose rules aren't in the repo is unauditable by the panel it convenes. Commit them.

  ### TOP 5 HIGHEST-LEVERAGE IMPROVEMENTS

  2. Ship the v2 header flow in the discovery docs *before* the flip and keep `/v1/*` as a Sunset-headered shim into the v2 pipeline instead of a bare hard cut (`reviews/cdp-findings.md:48-56`, `reviews/kaizen-log-2026-08-19.md:12`).
  3. Collapse the claim machine to D1-only (`UNIQUE(payer,nonce)` + guarded UPDATE), deleting the per-payment DO and the entire DO/D1-divergence bug class (`reviews/plan-rev3-2026-08-19.md:41-44`, `reviews/reconciler-gate.md:15-17`).
  4. Resolve ambiguous settles inline with a single `(from, nonce)` log query on the 503 path, keeping the hourly cron as backstop (`reviews/reconciler-spec-v1.md:56`, `reviews/reconciler-e2e-report.md:15-18`).
  5. Re-price against the measured $0.001/settle CDP fee (floor ≥10× marginal fee) and adopt `batch-settlement` for sub-cent tools (`reviews/cdp-findings.md:22,27`, `site/public/llms.txt:95-96`).

  ### IF I WERE REBUILDING FROM ZERO
  I'd build the smallest machine that is honest at every layer: one D1 ledger as the single claim authority (UNIQUE constraint for mutual exclusion, guarded UPDATEs for absorbing transitions, no Durable Object zoo to diverge from it), offering both spec flows — `authorization` as default so every off-the-shelf x402 client works at ~300ms, `upfront` for callers who want finality — instead of an upfront-only stance the spec itself tells clients to de-prefer; receipts as domain-separated EIP-712 typed data that the shipped SDK can byte-verify, published in the manifest; reconciliation pushed by chain-event webhooks with a cron sweeper as janitor, so a paid-but-unserved client is made whole on its first retry, not at the top of the hour; pricing derived from the facilitator's measured fee schedule with batch-settlement for sub-cent calls; and every machine-facing artifact (manifest, llms.txt, OpenAPI, pricing page, SDK constants) generated at deploy time from the same route configuration that stamps the requirements — because this review's worst findings are not crypto bugs but four public documents contradicting each other and the ledger, which is fatal for a product whose entire premise is verifiable consistency.
